# cc65816 5.18: `p->a = p->b OP x` through a pointer on the stack

Found while bringing up the file stubs (`test/readwrite.c`): a 256-byte
`fwrite()` to a freshly opened file overwrote the heap.  The cause is in
the C library's `__fs_fdopen`, and the cause of that is the compiler.

## The bug

Small data model.  A near pointer `p` that has to survive a call is kept
in a stack slot and addressed as `(d,s),y`, or copied to X and addressed
as `n,x`.  When the right-hand side of an assignment through `p` is one
binary operation whose *left* operand is another member (or element) of
the same `p`,

    p->a = p->b OP x;       /* or p[i] = p[j] OP x, i != j */

the load of `p->b` is done with the *destination's* offset, so the
statement becomes `p->a OP= x`.

    extern void f(void);

    void add(int *p)
    {
        f();
        p[2] = p[1] + 64;
    }

    $ cc65816 --core=65816 --code-model=large --data-model=small -O0 bug.c

        add:        phy
                    sta     1,s
                    jsl     long:f
                    ldy     ##4             ; offset of p[2]
                    lda     ##64
                    clc
                    adc     (1,s),y         ; reads p[2], should read p[1]
                    sta     (1,s),y
                    ply
                    rtl

Run on the target with `a[] = { 0, 100, 5 }`: `a[2]` comes out as 69
(5 + 64), not 164.  `-O2` produces the identical sequence.

The same happens with a struct, which is how the library meets it:

    struct s { int fd; char *a; char *b; };
    void fdopen_like(struct s *st)
    {
        st->a = m(64);
        st->b = st->a + 64;
    }

                    jsl     long:m
                    ldy     ##2
                    sta     (1,s),y         ; st->a = ...
                    iny
                    iny                     ; Y = 4, offset of st->b
                    lda     ##64
                    clc
                    adc     (1,s),y         ; reads st->b
                    sta     (1,s),y

## The exact trigger

From four matrices of variations (about seventy statements, each read in
the listing), the condition is: the right-hand side, after any casts and
parentheses, is **one binary operator whose left operand is a member or
element of the same pointer as the destination**, and the pointer lives
in a stack slot.

Triggers:

- Operators `+ - & | ^ <<`, and a signed `>>` (emitted as `ror n,x`).
  `p->a = p->b + 1` and `- 1` become `inc n,x` / `dec n,x` on the
  destination; `* 2` becomes `asl n,x`.
- Any element width: `char`, `int`, `long` (`adc ##64; sta 8,x; adc
  ##0; sta 10,x`).
- A variable index on either side is ignored along with the load:
  `p[n] = p[1] + 64` and `p[2] = p[n] + 64` are both wrong.
- `x` may be a constant, a global, a parameter, another member of `p`
  (then both loads take the destination's offset) or a product that
  goes through `_Mul16`.
- A cast round the whole right-hand side, `(int)(p->b + x)`, changes
  nothing.
- Two such statements in a row are both wrong.
- `-O0` through `-O2`, `--code-model=small` and `large` alike.

Does not trigger:

- the member on the right of a non-commutative operator: `x - p->b`,
  `g - p[1]`, `g() - p[1]`, `-p[1]`
- more than one operator at the top level: `(p->b + x) + y`,
  `p->b * 2 + x`, `(p->b + x) >> 1`, `(p->b + 7) / 8 * 8`
- a call or a library routine between the load and the store:
  `p[1] - g()`, `p[1] / 2`, `p[1] * 3`
- a cast on the left operand itself: `(unsigned)p->b >> 1`
- a comparison, `p[1] == 0`; a plain copy, `p[2] = p[1]`; a compound
  assignment, `p[2] += p[1]` (which is what the compiler thinks it was
  given)
- a temporary: `t = p->b + x; p->a = t;` or `b = p->b; p->a = b + x;`
- `p` still in X because no call spilled it; `p` a global; `p` a
  `__far` pointer; an alias, `q = p; q->a = p->b + x`
- `--data-model=medium`, `large` or `huge`

The rule for code that has to build with 5.18: **never write `P->a =
P->b OP x` through a near pointer; take `P->b` into a local first.**

The same defect has been met three times before in gem4xe, each time in
a narrower form -- a stack array (`x[d] = x[d-1] + ...`), a pointer
parameter with a computed index, and an in-place shift or decrement on
a dead pointer's slot -- and is pinned there as B1, B13, B5 and now B15
in `tools/ccbug/`, so that its `make check-cc` reports when a compiler
release fixes it.

## What it does to the library

`src/lib/stdio/__fs_fdopen.c`, the part of `fopen()` that builds a
`FILE`, has exactly this shape:

    if ((stream->fs_bufstart = malloc(BUFSIZ)) == NULL) ...
    stream->fs_bufend = &stream->fs_bufstart[BUFSIZ];

In `clib-lc-sd.a` (5.18) the second line is `fs_bufend += 64`, so every
stream `fopen()` returns has `fs_bufend` = whatever `malloc()` left in
that word, plus 64.  `__lib_fwrite` sizes its copy by
`fs_bufend - fs_bufpos`, which is then garbage, so a request longer than
the 64-byte buffer is copied in whole and the rest lands on the heap.
`__lib_fread` sizes its read-ahead the same way.  Short writes that fit
in the buffer happen to work, which is presumably why it has gone
unnoticed.

The library's other two data models (`-md`, `-ld`) do not have the
problem because the compiler gets those right.

## Workaround here

`src/fdopen.c` supplies `__fs_fdopen`; a library named before
`clib-*.a` on the link line wins, and the replacement computes the end
through a local.  It also sets `fs_next` to NULL (see below).  Remove it
when the fixed compiler is the minimum version.

## Two more library notes, found the same way

- `fgetpos()` returns the file descriptor's position; unlike `ftell()`
  it does not subtract the read-ahead still in the stream buffer
  (`lib_fgetpos.c` vs `lib_ftell.c`).  After `fgets()` on a buffered
  stream the two disagree.  `fseek(f, 0, SEEK_CUR)` first makes them
  agree; `test/readwrite.c` does that.
- `__fs_fdopen` never initialises `fs_next`.  `fclose()` unlinks a
  stream with `sl_head = next->fs_next` or `prev->fs_next = next->fs_next`
  (`lib_fclose.c`), so closing the stream at the tail of the list copies
  whatever `malloc()` left in that word into `sl_head` or the previous
  stream.  `fflush(NULL)` then walks the list from `sl_head`
  (`lib_libflushall.c`) and follows the garbage.  The next `fopen()`
  overwrites exactly that word again, which narrows the window enough
  to hide it.
